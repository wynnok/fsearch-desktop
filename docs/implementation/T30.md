# T30：普通文本与按文件匹配行

对应 [GitHub #44](https://github.com/wynnok/fsearch-desktop/issues/44)。用户明确要求继续代码实施；T27 的真实设备/权限门禁继续保留。固定上游为 `0.2.1 / 88e63fdf850cf7749deae8198b187accd21f8ba5`。

## 公开契约与界面

- 同一 Swift FsearchService 增加 `grep(ContentSearchRequest)`，经 C ABI 调用公开 `Engine.grep` 和 `Grep::new(..., Literal)`。不复制候选、内容索引或匹配算法，样本名称 Searcher 明确拒绝正文查询。
- 请求为非空普通文本，名称高级语法不解释正文；当前采用上游 smart case。响应保留 request ID、一文件一组的行/文本/UTF-8 范围、candidates/read、complete/next 与 indexed 来源。
- 搜索菜单提供独立“文本内容搜索…”窗口。按文件显示匹配行，分别标记文件数量与返回片段的匹配数，保留打开、Finder、复制路径及 Quick Look。输入变化丢弃旧响应/选择/预览，旧查询不覆盖新输入；正文不进入偏好或诊断白名单。
- T30 使用当前 Engine 根范围，尚不应用名称窗口范围/属性筛选（T31）；正则/显式大小写、cursor 续查及 Unicode 高亮分别留给 T31/T32。当前不高亮，避免把 UTF-8 字节直接当原生字符位置。
- 当前最多 100 个文件、每文件 5 条匹配行、片段约 400 UTF-8 字节、250ms 上游预算。`!complete || next != nil` 显示未完成；即使候选处理 complete，也不宣称所有匹配均已显示。来源区分内容索引候选与直接读取候选，不能据此宣称全盘覆盖。

## 当前使用边界

默认开发包仍是名称样本模式，在内容窗口查询会明确说明需要真实 Engine；它没有自动扫描个人磁盘或解除 T27。维护者可用明确指定、项目内隔离的 workspace 启动交互式真实内容入口：

```sh
bash scripts/dev.sh check
.build/debug/FsearchSample --content-workspace <workspace>
```

workspace 必须已有 `fixtures/`、相邻 `confinement-denied.txt`；独立 `index/` 由受限 Engine 创建。Seatbelt 在进程内阻止读取 fixture/index 之外的文件，进程退出终止 Engine；这是专用受控入口，不是对个人磁盘覆盖或正式权限的承诺。

只支持上游允许的文本、大小/忽略规则，直接扫描也有候选/大小限制；PDF/Office/OCR、压缩包和云端未下载正文不作为可搜能力。详细既有准入与资源限制见 [T09](T09.md)。预览能打开文件不等于正文能检索。

## 验证（2026-10-13）

用户确认 Swift 服务接缝由独立受限 Engine 进程执行，并补原生内容与文件动作。ContentSearchTests 启动 FsearchEngineCheck 的 content 阶段，用真实文件核对一文件两行、Unicode、CRLF 行号/文本、独立两处匹配与 UTF-8 `[0,10)` 范围、PDF 排除、无匹配及修改正文后新结果/旧正文消失。

最初在外层执行沙箱内运行时，sandbox_init 被拒绝，未启动 Engine；该失败不是功能 red 的证据。沙箱外运行相同入口后，由子进程自行安装既有 Seatbelt 策略，服务测试通过。没有以模拟 matcher 代替 Engine。

`bash scripts/content-validation.sh` 实际通过原生窗口与同一个服务运行：内容 sheet 显示 Unicode/CRLF 两行、打开真实目标、Quick Look 可见、无匹配以及最终诊断没有片段。截图 `.build/content-evidence/native/content-results.png`、脱敏成品 diagnostics.json 与 native.log 保留；临时 fixture/index 清理。既有名称原生旅程及更新 sheet 回归通过。
