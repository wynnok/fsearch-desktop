# T23：每日检测上游正式 Release

对应 [GitHub #37](https://github.com/wynnok/fsearch-desktop/issues/37)。本票只在仓库 CI 中检测上游正式 Release，并输出可追溯的现用/候选版本；不更新 `bridge/Cargo.toml`、`bridge/Cargo.lock`，不创建升级 PR，不合并，不发行，也不创建 Codex 定时任务。

## 选择契约

`scripts/check-upstream-release.sh` 从 `bridge/Cargo.toml` 与 `bridge/Cargo.lock` 读取当前固定的 Fsearch 版本和 commit，要求两份记录的 commit 一致。默认请求：

- `GET /repos/noahdunnagan/fsearch/releases?per_page=100`
- `GET /repos/noahdunnagan/fsearch/tags?per_page=100`

候选必须同时满足：

- Release 的 `draft=false`。
- Release 的 `prerelease=false`。
- `tag_name` 严格匹配 `vX.Y.Z`。
- 所选 tag 在 Tags 响应中解析为 40 位十六进制 commit。

候选在全部正式 tag 中取最高语义版本。`main`、其他非 `vX.Y.Z` tag、草稿和预发布都不会被选作正式依赖。输出明确记录选择策略、Release 数量、正式 Release 数量和被排除的 tag/原因。

JSON 结果包含：

- `current.version` 与 `current.commit`：当前锁定版本。
- `candidate.version`、`candidate.tag`、`candidate.commit` 与 `candidate.release_url`：本次选择的正式 Release。
- `selection.policy` 与 `selection.excluded_releases`：选择依据。
- `run_url`：CI 运行时提供的工作流运行链接。
- `error`：成功时为 `null`；失败时包含 `kind` 与 `message`。

成功且候选与当前 pin 完全相同时返回 `status=current`；候选版本或 commit 变化时返回 `status=update_available`。脚本不修改仓库文件；无更新时只输出结果，因此工作树保持不变。

网络请求失败、HTTP 错误、响应不是 JSON 数组、Release/Tag 元素结构无效、没有正式 Release，或所选 tag 无法解析到 commit 时：

- 保留 `current.version` 与 `current.commit`；
- 将 `candidate` 写为 `null`；
- 返回 `status=error` 和非零退出码；
- 不读取缓存，不使用预置版本，不伪造候选。

## 仓库 CI

`.github/workflows/upstream-release-check.yml` 每天 UTC 01:23 执行，并支持 `workflow_dispatch`。作业只有 `contents: read` 权限，输出：

- GitHub Step Summary 中的人类可读现用/候选/失败结果；
- `upstream-release-check` artifact 中的 `result.json` 与 `summary.md`；
- 结果中的本次 Actions run URL。

工作流没有 PR、commit、tag、release 或 Codex automation 步骤。Artifact 保留 30 天，后续每日运行会以新的 Actions run 和 artifact 记录结果。

## 受控测试

`scripts/tests/test-check-upstream-release.sh` 只替换公开的 GitHub Releases/Tags JSON 输入或 API base，不 mock 脚本内部函数：

- 无更新：当前 `v0.2.1` 与最高正式 Release 相同，结果为 `current`。
- 新候选：`v0.2.10` 与 `v0.3.0` 共存时选择语义版本最高的 `v0.3.0`。
- 预发布过滤：同时给出 draft `v0.5.0`、prerelease `v0.4.0`、滚动 `main` 和正式 `v0.3.0`，只选择 `v0.3.0`。
- 重复运行：同一输入执行两次，输出逐字节一致。
- 网络失败：不可达 API base 返回 `status=error`、`error.kind=network`、候选 `null`，当前 pin 保留。
- 接口失败：非数组 Releases 响应返回 `status=error`、`error.kind=api`、候选 `null`，当前 pin 保留。
- 可追溯输出：JSON 中的 run URL、选择策略、排除原因和 Markdown summary 一致。

`Tests/FsearchServiceTests/UpstreamReleaseCheckTests.swift` 将受控 shell 套件接入现有 Swift test target，不需要修改 `scripts/dev.sh` 或 `Package.swift`。

## 未验证项与残余风险

- 本机没有在 GitHub Actions 上实际触发 workflow；真实的定时执行、Step Summary、artifact 上传和运行 URL 只能在本提交进入默认分支后由 GitHub 调度或手动 dispatch 证明。
- 当前没有新正式 Release，真实 API 核对只能证明“无更新”选择路径和 tag 到 commit 的解析；真实“新候选”仍由受控 fixture 覆盖。
- GitHub API 在达到速率限制、返回截断列表或 tag 分页缺失所选 tag 时会进入错误路径并保留当前 pin；CI 提供只读 token 以降低无认证限流风险，但未在受限网络上验证。
- workflow 只检测并输出结果，尚未执行 T24 的依赖更新、兼容性门禁、升级 PR 或发布流程。
