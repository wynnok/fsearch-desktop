# T24：上游升级 PR 与兼容检查

对应 [GitHub #38](https://github.com/wynnok/fsearch-desktop/issues/38)。本票在 [T23](T23.md) 的每日检测之上，把 `update_available` 结果变成可审核的升级候选：固定候选 commit、刷新锁定记录、复用既有验证入口跑兼容检查、评估临时补丁并输出审计报告，最后交由维护者审核合并。作业不会自动合并、打 tag 或发 stable。

## 上下文缺口

复核前，仓库只有 [T23](T23.md) 的每日检测工作流 `.github/workflows/upstream-release-check.yml`，T23 正文明确记录“不创建升级 PR”。因此 T24 的检测→变更→PR→检查路径此前没有实现，本票在本次复核中补齐。

## 选择契约

`scripts/prepare-upgrade.sh` 读取 `scripts/check-upstream-release.sh` 的 JSON 结果：

- `status != update_available`（`current`、`current_ahead`、`error`）时保持无变更，写出 `no-op` 报告，退出码 0；其中的网络/API 错误由检测步骤自身非零退出，工作流失败且不产生变更。
- `status == update_available` 时校验候选 `version`、`tag`、`commit`（40 位十六进制），随后：
  - 改写 `bridge/Cargo.toml` 的 `rev`、`bridge/src/lib.rs` 的 `UPSTREAM_VERSION`，刷新 `bridge/Cargo.lock`；
  - 运行 `scripts/check-upstream-pin.sh` 复核三处 pin 一致；
  - 复用 `scripts/dev.sh check`（宿主构建与链接）、`scripts/architecture.sh build all release`（两架构构建与链接校验）与 `scripts/dev.sh test`（查询与快照回归）作为兼容检查；
  - 读取 `bridge/upstream-patches.json` 评估临时补丁；空列表即无私有 fork，不人为制造补丁；
  - 写出 `.build/upgrade/report.md`（人读）与 `.build/upgrade/result.json`（机器可读，含 `outcome`/`branch`/`checks`）。
- 任一步失败（锁定刷新、pin 校验、兼容检查）时保留候选改动与 `logs/` 诊断，`result.json` 的 `outcome` 为 `failed`，脚本非零退出，供工作流以 draft PR 保留候选。

脚本先 `source scripts/build-environment.sh`，使 `CARGO_HOME`/`CARGO_TARGET_DIR`/`RUSTUP_HOME` 落在项目内，锁定结果可复现。

`scripts/open-upgrade-pr.sh` 负责提交与开 PR：去重键为确定性的分支名 `upgrade/fsearch-v<version>-<commit12>`。远程已有同名分支时，基于远端 head 合入本轮已经检查的基线，恢复候选的三个 pin 文件，仅在变化时追加提交并正常 push，不做 force push。合并存在非 pin 冲突，或最终树与已验证基线存在非 pin 差异时停止，避免将通过报告附到未经检查的代码上。命中开放 PR 即更新标题、正文和 draft 状态，否则 `gh pr create`。失败候选保持 draft，后续通过可转为 ready。`git`/`gh` 可用 `FSEARCH_UPGRADE_GIT`/`FSEARCH_UPGRADE_GH` 覆盖以便受控测试。

`check-upstream-pin.sh` 已支持 `FSEARCH_PIN_CARGO_TOML` / `FSEARCH_PIN_CARGO_LOCK` / `FSEARCH_PIN_LIBRARY` 覆盖，`prepare-upgrade.sh` 通过 `FSEARCH_UPGRADE_ROOT`、`FSEARCH_UPGRADE_LOCK_COMMAND`、`FSEARCH_UPGRADE_COMPAT_COMMAND` 接受受控输入，无需网络、Swift 或 Cargo 即可复现完整路径。

## 仓库 CI

`.github/workflows/upgrade-pr.yml` 每天 UTC 02:23 在 `macos-14` 运行，并保留 `workflow_dispatch`：

1. 运行 T23 检测并记录 `status`；
2. 仅当 `update_available` 时运行 `prepare-upgrade.sh` 与真实兼容检查，并把候选 diff 写入 `candidate.patch`；
3. 通过 `open-upgrade-pr.sh` 提交三个 pin 文件到去重分支并开/复用 PR；检查通过为普通 PR，失败为 draft PR；
4. 若 `result.json` 的 `outcome` 不是 `pr-ready`，末尾 gate 步骤让作业失败；任何情况都不会自动合并、打 tag 或发行。

权限限定为 `contents: write` 与 `pull-requests: write`；检查产物上传为 artifact，保留 30 天。

## 受控测试

`scripts/tests/test-prepare-upgrade.sh` 在项目内 `.build/upgrade-tests/` 建临时 root，注入受控锁定刷新与兼容命令，覆盖：

- 无更新：pin 文件哈希不变，报告为 `no-op`；
- 新候选：Cargo.toml、lib.rs、Cargo.lock 更新到候选 commit，pin 校验通过，`result.json` 为 `pr-ready` 且分支名确定；
- 重复候选：重跑幂等，分支名（去重键）不变；
- 网络/API 错误：保留当前 pin，无变更，`no-op`；
- 兼容失败：保留候选改动与 `logs/compat.log`，`result.json` 为 `failed`，脚本非零退出。

`scripts/tests/test-open-upgrade-pr.sh` 用注入的 `git`/`gh` 覆盖 PR 段：新候选 push（`-u`）并开普通 PR；无文件变化的同名分支不重复提交或 push，既有 PR 刷新报告与状态；失败候选走 `--draft`。另以项目内真实 bare remote 验证首轮旧锁 draft、主分支兼容修复、次轮新锁成功的旅程：远端保留兼容修复及新锁，首轮提交仍为祖先，既有 PR 转 ready，第三轮无变化不再提交。
