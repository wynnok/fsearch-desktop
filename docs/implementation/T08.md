# T08：实际签名应用验证权限前后索引覆盖

对应 [GitHub #22](https://github.com/wynnok/fsearch-desktop/issues/22)，父规格 [SPEC-03](../specs/03-engine-validation.md) 的 V5 与 [SPEC-07](../specs/07-permissions-lifecycle.md) 的权限门禁。真实 TCC 变化只能由维护者在专用 macOS 环境手动执行；本机没有 Developer ID Application 与专用 TCC 环境，因此本票门禁保持未验证。

## 公开契约

### 默认 Engine 专用入口

`fsearch_real_engine_open(const char *index, char **error)` 是默认、非受限真实 Engine 的 C ABI。它与 `fsearch_engine_open` 的 Seatbelt fixture 路径分离，启动条件为：

- `FSEARCH_PERMISSION_ENV=dedicated`。
- `FSEARCH_PERMISSION_WORKSPACE` 指向已存在、已规范化的绝对工作区。
- 该工作区根目录存在 `.fsearch-permission-workspace` 标记文件。
- 索引目录为绝对路径并位于该工作区内，创建或解析后仍不能是工作区外路径、`HOME` 或 `/`。
- 每进程只允许一个 Engine；关闭句柄不代表终止上游 worker，完整停止仍由进程退出保证。

默认入口使用 `Options { dir: 调用者索引目录, home: 真实 HOME, skip: None }`，保留上游 FDA 探测、默认名称索引与内容索引，不安装 Seatbelt，不复制内核，不切换 helper。

Swift 公开入口为 `FsearchService(realEngineIndexDirectory:)`。普通开发进程调用时，Rust 在创建索引目录和启动 Engine 前返回可读错误，Swift 将其包装为 `FsearchError.initialization`。

### 权限证据模型

`FsearchService` 公开以下 Codable 模型：

- `PermissionValidationPhase`：`skip`、`grant`、`recheck`、`restart`、`revoke`。
- `PermissionProtectedLocationEvidence`：位置、sentinel、存在性、直接读取、完整搜索命中。
- `PermissionICloudEvidence`：配置路径、索引前后 stat、ubiquitous 状态与 `notMaterialized` / `materialized` / `unverified` 判定。
- `PermissionProbeEvidence`：单阶段状态、位置证据、iCloud 证据、`contentSettled` / 原因和阶段评估。
- `PermissionValidationReport`：Developer ID 签名与全部阶段证据的最终 `verified` / `unverified` 汇总。

`fullDiskAccess` 只作为状态快照记录。所有阶段都要求 sentinel 确实存在，阶段评估和最终报告再要求受保护位置的直接读取与完整搜索命中符合该阶段预期；单独为 `true` 不会让门禁通过。`skip` / `revoke` 中缺失的 sentinel 也会失败，不能以“不可读、未命中”空过。

## 隔离与人工权限步骤

`--permission-probe <phase> <config.json> <output.json>` 是签名 bundle 内的专用模式。config 形式如下：

```json
{
  "indexDirectory": "/absolute/dedicated/workspace/index",
  "protectedLocations": [
    {
      "name": "protected-example",
      "path": "/Users/example/Protected",
      "sentinelName": "fsearch-coverage-sentinel.txt"
    }
  ],
  "iCloudPlaceholder": "/Users/example/Library/Mobile Documents/example.icloud"
}
```

探针在 Engine 创建前采样 iCloud，等待真实索引 ready，再等待 `contentDocs > 0 && contentPending == 0` 以确认内容索引确实已经活动并收敛；默认最长等待 300 秒，可由 `FSEARCH_PERMISSION_CONTENT_SETTLE_SECONDS` 覆盖。仅看到 `contentPending == 0` 不足以判定收敛，因为内容索引尚未开始时该条件也会瞬时成立。超时不会崩溃，但会记录 `contentSettled=false`，原因同时包含 `contentDocs` 与 `contentPending`，阶段 assessment 必须失败，最终 gate 保持 `unverified`。iCloud after 在收敛等待结束后采样，因此覆盖 ready 之后仍进行的内容索引活动，而不是只覆盖 Engine ready 的瞬间；代码只读取文件大小和 ubiquitous 状态，不调用下载 API，不修改 ACL、TCC 或磁盘权限。

若专用环境没有可索引文本，`contentDocs` 可能始终为 0。此时本票保持未验证，不能把“没有观察到索引活动”当作 iCloud placeholder 未物化的证据。

探针继续逐个位置记录 sentinel 是否存在、能否直接读取一个字节、按 sentinelName 的完整搜索是否命中，以及完整 `ServiceStatus`。

上游 `walk::SKIP` 是进程级 `OnceLock`。M1 没有实现应用内动态重新检查，`recheck` 和 `restart` 都通过新的专用进程重新加载 Engine 并重新探测；`restart` 额外要求先完全退出并重启签名应用。报告不得把这些阶段解释为应用内热重检，该能力属于后续产品行为。

维护者必须手动完成以下外部步骤，脚本不会代替：

1. 在专用 macOS 13+ 环境准备独立工作区标记、受保护位置 sentinel、iCloud placeholder、测试配置和 Developer ID Application 签名的 `FsearchSample.app`。
2. 在授权前运行 `skip`。
3. 在系统设置中手动授予完全磁盘访问并运行 `grant`。
4. 为一个新的专用进程运行 `recheck`；该进程重新加载 Engine，但不声称应用内热重检已经实现。
5. 完全退出并重新启动签名应用后，再为新的专用进程运行 `restart`。
6. 在系统设置中手动撤销权限，完全退出并重新启动签名应用，再为新的专用进程运行 `revoke`。

## 可复现入口

```sh
export FSEARCH_PERMISSION_ENV=dedicated
export FSEARCH_PERMISSION_WORKSPACE=/absolute/dedicated/workspace
export FSEARCH_PERMISSION_APP=/absolute/signed/FsearchSample.app
export FSEARCH_PERMISSION_CONFIG=/absolute/dedicated/permission-config.json

# 标记文件由维护者准备，preflight 只验证，不自动创建。
test -f "$FSEARCH_PERMISSION_WORKSPACE/.fsearch-permission-workspace"

bash scripts/permission-validation.sh preflight
bash scripts/permission-validation.sh probe skip
bash scripts/permission-validation.sh probe grant
bash scripts/permission-validation.sh probe recheck
bash scripts/permission-validation.sh probe restart
bash scripts/permission-validation.sh probe revoke
bash scripts/permission-validation.sh report
```

证据写入 `.build/permission-evidence/`。`preflight.json` 记录专用环境、工作区标记、`.app` 路径、`codesign --verify`、签名 Authority 与 TeamIdentifier；只有全部前置成立时 `gate=ready`。每个 probe 另有 `<phase>.execution.json`，记录完整命令、退出码和时间戳。`report.json` 只有在签名前置为 ready、五个阶段评估全部通过且每阶段 iCloud 均为 `notMaterialized` 时才写 `gate=verified`。

## Red 到 Green

先新增 `Tests/FsearchServiceTests/PermissionCoverageTests.swift`，再运行：

```sh
bash scripts/dev.sh test --filter PermissionCoverageTests
```

初始红灯是编译失败，缺少 `PermissionProbeEvidence`、`PermissionValidationPhase` 和 `PermissionSignatureEvidence`。后续审查红灯包括缺失 sentinel 的 `skip`、未收敛的 `grant`，以及 `contentDocs=0 && contentPending=0` 被误当作已收敛；这些场景都曾错误判为 `verified`。修复后同一命令通过 6 个测试：

- 非专用环境调用 `FsearchService(realEngineIndexDirectory:)` 被拒绝，且索引目录未创建。
- 缺 Developer ID 签名或缺任一阶段时报告保持 `unverified`。
- `fullDiskAccess=true` 但 grant 阶段缺少真实受保护位置搜索命中时报告保持 `unverified`。
- iCloud placeholder 被判定为已物化时报告保持 `unverified`。
- 任意阶段 sentinel 不存在时报告保持 `unverified`，包括 `skip`。
- `contentPending != 0`、`contentSettled=false`，或 `contentDocs=0 && contentPending=0` 时报告保持 `unverified`。

## 本轮实际验证

2026-10-13 在项目根目录执行：

```sh
bash scripts/dev.sh test --filter PermissionCoverageTests
bash scripts/dev.sh test
bash scripts/dev.sh check
bash scripts/permission-validation.sh preflight
bash scripts/permission-validation.sh report
```

过滤测试 6 项通过；完整服务测试 33 项通过；`dev.sh check` 的 Rust check、Swift 构建与链接通过。未设置专用环境时，`preflight` 写入 `gate=unverified` 并以非零退出；随后 `report` 也写入 `gate=unverified` 并以非零退出。`probe skip` 在 preflight 未通过时直接拒绝，未启动 Engine。未运行默认 Engine probe，未触发全盘扫描，未执行 `tccutil`，未写 TCC 数据库或 `defaults`。

## 未验证门禁

本机只有 ad-hoc 签名产物，没有 Developer ID Application 身份，也没有受控 TCC 专用环境。因此以下事项仍为未验证，T08 权限门禁保持关闭：

- 实际签名应用的 skip、grant、recheck、restart、revoke 真机结果。
- 受保护位置授权前后的索引覆盖变化。
- 真实内容索引从 ready 到 `contentPending == 0` 的等待结果，以及收敛后 iCloud 真实 placeholder 保持未物化。
- macOS 13 专用设备与正式签名主体的 TCC 身份稳定性。

这些项只能在维护者提供签名凭据和专用环境后执行。受控合成测试、`fullDiskAccess=true`、终端权限或脚本逻辑都不得替代上述证据。
