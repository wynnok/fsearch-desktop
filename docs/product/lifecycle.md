## 后续实现顺序

1. 引擎集成和排序/完整性契约，先做合成索引与受控文本 fixture，不先扫描整盘。
2. 单窗口真实名称搜索，连接输入、范围、结果和索引状态，验证旧响应不会覆盖新请求。
3. 全局排序与分页、过滤、选择稳定性；特别覆盖大量同名文件与跨页边界。
4. 检查器、Quick Look、路径导航和系统打开操作，再补错误/权限/文件消失状态。
5. 双架构 CI、可安装 DMG、签名方案和安装后 TCC 验证。
6. 内容搜索和 beta 功能；先确保预算/游标/结果完整性语义，再做匹配片段展示。

| 文档 | 维护规则 |

## 质量门禁

功能验证用受控目录和合成索引，含中文/Unicode、路径特殊字符、重复名称、大小/时间同值、符号链接、目录增删改、应用包和权限拒绝。关键契约需要自动化测试；不为静态文档写镜像测试。

性能先做首屏、全量排序、内容预算、索引变化和空闲状态的不同测量，记录 p50/p95、RSS 峰值和样本数量。最低 OS、Intel 实机、Apple Silicon 实机都要有记录；不能把跨编译通过等同于运行通过。

更新验证使用旧版本数据和新版本应用进行启动/恢复/查询。旧格式不兼容时依据 Fsearch 的行为重建，清楚说明耗时；用户文件不作迁移。用户目录、索引和权限不在测试中被静默修改。

上游跟进从 M1 建立每日正式版检测、自动升级 PR 及兼容性/双架构检查，首个可安装版本即保留升级通路，不等正式发布后才考虑。固定研究源码记录历史事实；每次批准升级时补充新版本差异，不把历史调查改写成对新版本的保证。临时补丁记录测试、来源与移除条件，升级时评估删除；检查通过后维护者合并，版本 tag 触发 Releases 发行，当前尚无自动工作流。

首版检查更新提供下载链接，由用户手动安装；公开正式版必须通过签名公证与安装验证，alpha 开发测试包明确标注未公证。索引与设置本地保存，默认不持久保存搜索历史；诊断仅主动导出，默认去除完整路径和内容，验收需检查上游日志与错误信息的脱敏。

## Issues 工作流

GitHub Issues 为需求、规格和缺陷的唯一任务入口，文件文档为长期知识。本次已有一个总规格和 13 个子规格，全部应用 ready-for-agent 标签，父子与阻塞关系已建立；范围、验收、依赖和风险均写入正文。本地规格副本与 Issues 保持同步，执行状态以 GitHub 为准。

`needs-triage` → 明确信息后 `ready-for-agent` / `ready-for-human`；需要补充时 `needs-info`；不采用则 `wontfix`。状态变更附简短理由；不要仅因任务复杂而把它标成需人工。

提交/推送只在用户明确要求时进行；发布正式版本依照仓库约定确认。版本错误时保留历史、记录问题和提供修复版本，不重写已共享 Git 历史。
